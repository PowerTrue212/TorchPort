# 架构说明

## 依赖方向

```text
dsh-torchport ──调用──> torchport 命令行或服务接口
                           │
                           ├── 框架适配器
                           ├── 迁移与验证核心
                           └── 硬件执行后端
```

TorchPort 核心不得导入 DSH。DSH 插件可以依赖 TorchPort，并负责会话、审批、进度展示和任务恢复。

## 五类稳定契约

1. 项目检查结果：描述源框架、入口、权重、依赖和风险。
2. 统一迁移表示：描述计算图、权重、训练状态、源位置和验证探针。
3. 运行证据：描述环境、输入、输出、中间结果、性能和依赖残留。
4. 修复记录：描述触发条件、代码修改、数值变化和适用版本。
5. 验证证书：汇总双端运行环境、输入哈希、权重加载量、证据数量、两档容差
   结果和首次分歧；DSH、持续集成和可视化只消费该稳定结果，不解析运行日志。

仓库级证书的通过条件是输入哈希相同、源检查点完整、目标权重完整且 FP32 推理
通过。严格算子结果继续用于诊断。没有请求检查点时只检查目标权重；发现多个源端
候选时停止并要求选择，避免用随机模型签发证书。

## 验证工作流

```text
torchport verify
      │
      ├── PyTorch 源端执行 ──> evidence.json + tensors.npz
      ├── Jittor 目标端执行 ──> evidence.json + tensors.npz
      ├── fp32-inference ─────> 推理迁移验收
      ├── operator-strict ────> 算子差异诊断
      └── certificate.json ───> DSH / CI / 可视化
```

严格算子诊断不直接否决 FP32 推理证书。证书必须同时保留两档结果，使调用方既能
判断迁移是否满足使用要求，也能看到第一个尚未逐算子复现的位置。

证书中的 `first` 只表示当前档位的验收分歧点；`first_any` 表示包括非门控诊断
张量在内的第一个任意分歧点。这样 `fp32-inference` 可以在主输出和输入均通过时
签发证书，同时保留额外探针缺失或轻微算子差异作为诊断信息。

## 仓库级自动迁移

```text
任意 PyTorch 仓库
        │
        ├── 静态扫描：入口、依赖、权重、自定义算子、动态 API
        ├── 隔离复制：不修改源仓库、不覆盖已有输出
        ├── 路线选择
        │      ├── JTorch：代码不变，替换隔离运行环境
        │      └── 原生 Jittor：确定性源代码编辑
        ├── 按需生成 portlib：数据、优化器和调度器适配
        ├── Python 语法、依赖残留与目标端运行检查
        ├── 模块索引：包路径、导入别名、模型类与跨模块工厂
        ├── 配置求值：字面量、容器、JSON/YAML、参数展开
        ├── 参数求值：argparse 默认值、类型、dest 与布尔动作
        ├── 环境契约：显式值、源码默认值与子进程环境隔离
        ├── 探针覆盖：显式模型名、构造参数、输入形状与结构化输入
        ├── 权重归一：检查点包装、训练前缀、形状与加载完整性
        ├── 通用探针：结构化输入、构造参数、逐模块与函数式输出
        └── manifest.json + check.json + certificate.json + auto.json
```

仓库接入成功和迁移验收通过是两个不同状态。所有仓库都应能产生清单；只有没有
阻塞项、目标端真实运行成功且数值对齐通过后，才能签发最终验证证书。

`torchport auto` 是端到端编排层，只调用迁移器、运行检查和通用对齐器，不持有
新的转换规则。它的报告把三段结果合并为一个状态：`partial` 表示迁移清单仍有
阻塞项，`checked` 表示目标端检查通过但没有完成数值证书，`verified` 表示证书
通过。DSH 和 CI 可以优先读取 `auto.json`，需要排查时再下钻到低层报告。

`auto.json` 的 `advice.actions` 是智能体下一轮决策入口。每个动作包含稳定编号、
阶段、建议补充的命令行参数和示例值。探针缺构造参数时输出 `set-args`，缺输入
规格时输出 `set-input`，多个权重候选时输出 `set-weights`，运行或对齐失败时输出
对应的 `fix-runtime`、`fix-align` 或 `fix-parity`。这些动作只描述下一步，不自动
读取用户环境或覆盖已有产物。

`set-model` 动作会携带 `candidates`，由同一套仓库模块索引静态产生。候选包括
继承 `Module` 的模型类，以及返回这些模型类的工厂函数；每个候选记录点号名称、
文件、必需构造参数和 `forward` 输入名。候选排序优先入口文件内对象和无必需构造
参数对象，但不会执行仓库代码来验证构造是否成功。

候选还会记录可证明的 `defaults`、`hints` 和 `example_kw`。默认值来自函数签名；
提示值来自模块常量、静态字典和类属性，例如 `WIDTH = 4` 或 `Config.width = 4`。
`set-args` 会优先使用与当前模型匹配的 `example_kw` 生成 `--model-kw` 示例；缺失
的字段仍保留为占位符，避免把猜测值当成已验证配置。

`--try-hints` 只自动重跑一次，并要求迁移阶段动作都可由高置信建议满足。它可以
采用 `set-model` 的候选、`set-args` 的完整示例和 `set-input` 的 `input_specs`；
遇到 `set-entry`、占位符或通用图像输入占位时不会重跑。重跑输出写入新的
`*-hints` 目录，原始 `auto.json` 保留，最终报告通过 `retry` 和 `attempts` 记录
两次尝试的关系。

输入描述由 `shape`、`dtype`、可选的关键字参数名 `arg` 和字典字段名 `key` 组成。
简单位置参数和结构化调用共用同一采集流程；源端生成的输入归档由目标端读取，
证书同时核对整体输入哈希，避免双端各自随机生成导致的假分歧。

序列参数由 `pack` 和 `item` 描述，模型的列表、元组和字典返回值按稳定顺序展平。
全部 `output.*` 张量都属于推理验收门控项；中间模块和函数式算子仍作为诊断探针，
因此“主输出一致但辅助输出错误”不会获得通过证书。

仓库发现阶段会为根目录和 `src` 布局建立模块索引，并递归解析显式导入别名。
模型创建优先选择入口真实调用的工厂，其次选择入口调用的模型类，最后才回退到
仓库内无需构造参数的模型。探针保存入口可访问名称，不要求把模型复制到入口文件。
当训练入口调用了外部模型类时，探针入口可以切到模型定义文件；运行检查采用
`probe-import` 验证模型入口，避免执行训练循环、数据下载或顶层命令行逻辑。

配置求值只处理可证明且能写入 JSON 的静态值，包括仓库内 JSON/YAML、字典合并、
属性、下标、`*args` 和 `**kwargs`。环境变量只接受迁移命令显式提供的值或源码默认
值，并保存成执行契约；静态求值不会读取宿主机环境。它不执行仓库训练逻辑；Hydra
运行时组合和远程配置仍保持为显式未解析状态。

`argparse` 的 required 参数不会被猜测。只有 README 中出现面向同一入口的示例命令
时，系统才把命令里的参数值作为高置信提示值，用于恢复模型构造参数和
`--try-hints` 自动重跑。示例命令支持 `python train.py`、`python -m package.train`
和反斜杠续行；也支持 `torchrun -m package.train`、`accelerate launch -m
package.train` 这类 launcher。解析时从真实入口 token 后开始读取参数，launcher
自身参数不会进入模型构造提示。解析结果只进入探针提示，不替代运行证书。

配置入口按同一原则处理。README 中的 `-c/--config configs/model.yaml` 会先进入
`argparse` 静态模拟，再通过可证明的 `Path`、`open()`、`json.load` 或
`yaml.safe_load()` 读取本地配置文件。只有能序列化为 JSON 的值会进入模型构造
参数；动态配置组合仍保持未解析状态。

OmegaConf 入口走同一静态路径。`OmegaConf.load(args.config)` 被视为本地 YAML
读取，返回普通字典；后续 `cfg.model`、`OmegaConf.to_container(cfg.model)`、
`**cfg.model` 和模型构造参数反推输入形状继续复用通用求值器，不引入 OmegaConf
运行依赖。

模型注册表入口也只走可证明的静态路径。`import models` 会被记录为模块引用；
当训练脚本出现 `models.__dict__[args.arch](...)` 或
`builder = getattr(models, args.arch)` 时，系统先用 README/argparse 提示恢复
`args.arch`，再把调用目标解析成具体的 `models.smallnet` 这类工厂或类。此时探针
入口切到模型模块本身，避免运行训练脚本的参数解析、数据下载和训练循环。

常见第三方工厂入口采用同一机制。对于本地可解析的 `timm.create_model(...)` 和
`torchvision.models.get_model(...)`，系统会保留真实工厂调用参数用于运行证书，
同时静态分析工厂内部 `return Model(...)` 的参数转发，用这些模型构造参数推断输入
形状。这样不会把 `args.model` 误当作模型类的第一个构造参数。

Hydra 入口只做静态实例化解析。`instantiate(cfg.model)` 会在 `cfg.model` 是本地
YAML/OmegaConf 字典且包含字符串 `_target_` 时生效；系统把 `_target_` 解析到本地
模型类或工厂，并把除 `_target_`、`_args_` 等 Hydra 元字段以外的配置项作为构造
参数。目标端运行证书直接加载解析后的本地模型入口，不执行 Hydra 装饰器或训练脚本。

自定义注册表入口沿用工厂分析。对于 `build_model(cfg.model)` 这类函数，如果函数
内部把配置复制成字典、通过 `cfg.pop("type")` 取模型名，并从 `MODELS[type]` 里取
本地模型类，系统会静态绑定参数、解析注册表字典，再用剩余配置推断模型构造参数。
当工厂来自训练入口之外的模块且第一个参数是配置字典时，探针入口会切到工厂模块，
避免运行 argparse、数据加载或训练循环。

字符串动态导入只做可证明解析。`importlib.import_module(name)` 在 `name` 能由
本地 JSON/YAML、argparse 默认值或 README 命令恢复成确定字符串时，会被表示为
模块引用；后续 `getattr(module, class_name)` 若 `class_name` 也是确定字符串，
会继续解析到本地模型类。系统不会执行真实导入副作用，也不会猜测不确定字符串。

装饰器注册表会在模块索引阶段静态收集。`@MODELS.register_module()` 使用类名作为
注册键，`@MODELS.register("tiny")` 使用装饰器参数作为注册键；这些映射会在分析
工厂函数时预置到模块环境里。因此 `model_cls = MODELS[type]` 可以被解析成具体
模型类引用，而不需要构造或执行真实 Registry 对象。

注册表构造函数可以接收整份配置。`build_model(cfg)` 内部再访问 `cfg.model` 或
`cfg["model"]` 时，静态求值器会先从本地 YAML/OmegaConf 恢复整份配置，再在工厂
分析阶段绑定形参并解析内部属性或下标访问。只有当这些访问能落到本地 JSON/YAML
可序列化值时，才会生成 ready 探针。
证书执行阶段仍通过 JSON 传递探针参数；如果工厂需要 `cfg.model` 这类属性访问，
探针会把配置字典恢复成同时支持属性和下标访问的轻量配置对象后重试，不改变公开
`probe.json` 格式。

YACS 配置入口用轻量对象模拟，不引入真实 `yacs` 依赖。`CfgNode()`、配置属性赋值、
`merge_from_file(path)` 和 `merge_from_list(list)` 会在静态求值阶段合并成本地
字典；点分路径如 `MODEL.WIDTH` 会写入嵌套配置，并对数字、布尔值和列表做基础
类型解析。当入口模块导入本地 `get_cfg()` 这类无副作用配置函数时，系统会用该函数
所属模块的静态环境执行它，再回到入口模块继续合并配置。

当静态求值无法证明模型名、构造参数或输入时，迁移命令可以接收显式探针覆盖。
覆盖结果写入同一份 `probe.json`，后续运行检查和数值对齐不再重复猜测；如果覆盖
不匹配真实模型，目标端执行或双端证书会失败并给出运行错误，而不是在迁移阶段
假设成功。

原生迁移只有在通用探针状态为 `ready` 时才能没有探针阻塞项。缺少模型、构造参数
或输入会分别生成稳定编号的清单项；JTorch 路线保留为警告，原生 Jittor 路线视为
阻塞，避免把“代码已编辑”与“模型可验证”混为一个状态。

## 迁移执行原则

- 规则驱动的确定性修改优先于模型生成修改。
- 每个修改在独立工作树中执行。
- 运行成功不等于迁移成功，必须完成对应级别的数值对齐。
- 大模型采用分层探针和二分定位，避免保存全部中间张量。
- 跨硬件准确性验证与性能验证分开判定。
